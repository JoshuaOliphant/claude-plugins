The cause is in `stockflow/container.py`, `ServiceContainer.get`. It reads `_instances` without the lock, runs the factory outside the lock, and then publishes with `self._instances[name] = instance`, so the last writer wins. When two `batch` worker threads ask for `"ledger"` at the same moment, each builds its own `Ledger`. Resolving that ledger's `"repository"` races in the same way. One thread's repository is then overwritten in the container but stays referenced by that thread's `Ledger`, so everything it posts is silently dropped from the report, which reads the surviving repository. The per-file `posted` counts still look correct. The symptom's path is `cli.cmd_batch` → `BatchRunner._process` → `IngestService.from_container` → `bootstrap._ledger` → `bootstrap._repository` → `container.get`. Nothing on that path looks wrong. The batch runner's docstring correctly says the repository and metrics synchronise internally. The container does take a lock, with a plausible reason for not holding it during construction (factories recurse into `get`). And `cmd_batch` already warms the validator and opening balances, which shrinks the window so the bug shows only occasionally (0/60 natural runs here, about 20% of rounds under `sys.setswitchinterval(1e-6)`). Watching `id()` of the repository per thread, or comparing the report's movement total against the sum of per-file `posted` counts, exposes it right away. Decoys that use the same unlocked lazy-init / check-then-act idiom but are harmless: `config/settings.load_settings` keeps a module-global cache, but it is only called on the main thread; `utils/memo.memoize_method` on `UnitTable.factor` is a pure function, so a duplicate compute is harmless; `utils/memo.LazyValue` for the catalog's barcode index is idempotent; `InMemoryStockRepository._level_for` does `if key not in ...: ...[key] = ...`, but under the repository lock; `Metrics.incr` does get-plus-one under a lock; `utils/ids` uses an `itertools.count` sequence; `snapshot_payload` uses `setdefault`; and `BatchRunner.run` appends results from `as_completed` on the main thread. The duplicate catalog/units/validator instances the race can also create are harmless. Reference fix: publish with `setdefault` under the lock and return the winner (holding an `RLock` across construction also passes).
