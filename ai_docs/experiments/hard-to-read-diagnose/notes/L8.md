# L8 notes: quadratic scaling in a hot path

The cause is in `stockline/adapters/store.py` and how `stockline/adapters/repository_base.py` uses it. `MemoryStore.revision` is one counter for the whole store, bumped by a write to any namespace. `IndexedRepository._ensure_indexes` uses that global counter to decide whether its SKU and supplier-part indexes are stale. The repository's own `_put` keeps its indexes up to date and re-syncs to the counter. But for every created or updated row, `CatalogService.apply` publishes an event, `ChangeJournal` (subscribed in `bootstrap`) appends a `journal` record, and `Sequences.next` writes to `meta`. Every `progress_every` rows the run record is written to `runs` as well. Each of those writes moves the global revision. So the next `find_by_sku` in `Matcher.match` sees a stale index and rescans the whole `products` namespace, once per row: O(rows × catalog). Someone following the symptom's path (`cli → ImportService.import_file → pipeline → Matcher.match → find_by_sku`) sees a loop that does one indexed lookup per row. The index logic looks right on its own, and the per-row writes that defeat it happen through the event bus in other modules. They only show up when you count rebuilds or store reads at runtime. 8,000 rows take about 85 s buggy and 0.9 s fixed. The reference fix keeps a per-namespace revision and has the base repository compare against its own namespace's revision (making `_ensure_indexes` ignore foreign writes in any other way also passes). Decoys that use the same idioms but are harmless:
- `SupplierRepository` uses the same `IndexedRepository` and revision check, but it is looked up once per import over three records.
- `CatalogRepository.search_name` scans the whole catalog per call, but only for rows with no SKU and an unknown part number.
- `JournalRepository.entries/for_sku/for_run` sorts and scans the full journal, but only for the `history` CLI.
- `RunRepository.all/latest` scans and sorts, and the run-id collision `while` loop.
- `pricing.load_rules` is called for every row, but it is `lru_cache`d.
- `display_name` is `lru_cache`d.
- `ALLOWED_UOMS` is a list membership test per row, but a constant eight items.
- `RecentWindow` does a deque `in` per row, but bounded at 64.
- `reporting.supplier_summary` sorts inside a loop, end-of-run only.
- `CategoryTree.lineage` walks parents per row (depth ≤ 3).

The hidden test counts every record the store returns (a `MemoryStore` subclass passed to the public `build_app(store=...)`) during an all-update nightly import of N=400 vs N=800. It asserts linear growth plus a hard cap. Buggy: 161k → 642k reads. Fixed: 1.2k → 2.4k.
