# NOTES

The bug lives only in the shipped database `tree/data/stockroom.db`. There, the trigger `trg_stock_levels_touch` (`AFTER UPDATE OF on_hand ON stock_levels WHEN NEW.on_hand <> OLD.on_hand`) is meant to stamp `updated_at`, but it also runs `reserved = MIN(reserved, MAX(NEW.on_hand, 0))`. That clamp throws away backorder reservations whenever on-hand changes, whether by a receipt, a shipment, a cycle count or a transfer. The symptom's path is `receive` → `InventoryService.receive` → `repo/stock.apply_delta` (a plain `SET on_hand = on_hand + ?, reserved = reserved + 0`), then `report availability` → `ReportService.availability` → the `v_availability` view → `AvailabilityRow.available/backordered`. All of that Python is correct, and reading it predicts the right answer (10 reserved, 0 available). The trigger was created in the squashed baseline schema (versions 1-6), so it appears nowhere in the Python source, the README or the migrations module. You can only see it by running the flow and noticing that `reserved` changed with no code writing it, or by dumping the database schema. Decoys:

1. The `v_availability` view, defined in Python (migration 9). It uses a CROSS JOIN, a LEFT JOIN and an `active` filter, so it looks suspicious, but it is correct.
2. Migration 8, an `UPDATE stock_levels SET reserved = 0 WHERE reserved < 0` clamp on reservations. It is one-shot and already applied.
3. The `min(line.remaining, max(level.on_hand, 0))` clamp in `OrderService.ship`.
4. The `max(...)` clamps in `StockLevel` and `AvailabilityRow` for available and backordered.
5. `Catalog`'s in-process product cache, the `config._cached` settings global, and the `INSERT OR IGNORE` in `ensure_level` and `next_number`.
6. Unit-of-measure conversion and moving-average cost on receipt.
7. Three other column-rewriting or guarding triggers in the same database, all correct: `trg_orders_touch`, `trg_order_lines_fulfilled` (which rewrites `status`) and the append-only guards on `stock_moves`.

The reference fix adds migration 10, which recreates the trigger without the clamp. Editing the .db directly, or working around it in code, would also satisfy the tests. The tests assert only the CLI's availability/open-orders JSON output and order-placement exit codes.

The database is built by `build_db.py`, which is kept outside `tree/`.
