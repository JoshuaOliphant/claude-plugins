The cause is a stray, normally git-ignored dotfile `tree/.env.local` containing `RELAYDESK_BATCH=20` (an old developer setting). At start-up `cli.main` -> `bootstrap.start` -> `bootstrap.prime_environment` -> `utils.envfile.load(paths.env_files(root))` copies `.env` and then `.env.local` into `os.environ`, and `settings/loader.env_layer` maps `RELAYDESK_BATCH` onto `delivery.batch_size`, so the environment layer (correctly ranked above the config file) silently beats the value everyone edits. Someone reading the symptom's path (`send` -> `Dispatcher._batcher` -> `Batcher.build`, or the TOML loading in `settings/loader.py`) sees correct code: the batcher chunks by the configured size, the TOML layering and precedence are textbook, and `config` simply shows `batch_size 20`. The file is hidden from `ls`/glob and from ripgrep's default search (dotfile, and listed in `.gitignore`), and nothing in it mentions `batch_size`; it only surfaces when a repro inspects which layer supplied the value or dumps `os.environ` after bootstrap. Decoys: (1) the loader's optional `config/relaydesk.local.toml` override layer plus a shipped `relaydesk.local.toml.example` (the real override file is absent); (2) `templates/overrides/urgent.txt`, an override directory that does win over the stock template, intentionally; (3) `[defaults]` merging in `data/routing.toml`/`services/routing.py`; (4) `settings/coerce.parse_bool` and `RetryPolicy`'s `os.environ.get("RELAYDESK_RETRY_JITTER", "0")`, which look like the classic '0'-is-truthy trap but parse correctly; (5) the literal 20 elsewhere: `rate.burst = 20` in schema and config and `list --limit` default 20 in the CLI; (6) the documented `.env` file, which only sets values matching the config file. Valid fixes: delete `.env.local`, stop loading it, or otherwise make the config-file value effective without breaking real env vars and CLI flags (the tests check both still override).
