The cause is `to_epoch()` in `tree/tillbook/utils/timeconv.py`, which turns an aware datetime into epoch seconds with `time.mktime(moment.timetuple())`. `timetuple()` drops the tzinfo and `mktime` reads the wall-clock fields as server-local time, so on a non-UTC server every window bound moves by the server's UTC offset (−5:30 on an IST box, +8:00 on a Los Angeles box). The symptom's path looks correct at every step a reader would check first: `cli.cmd_daily` → `ReportService.daily_totals` → `LedgerService.transactions_on` → `Office.day_bounds()` builds the office-local midnight-to-midnight window properly with `zoneinfo` and converts it to aware UTC. The window is only lost three hops down, where `TimeIndex.between()` calls the innocent-looking `to_epoch()` to bisect its integer epoch keys. Those keys come straight from the data and are correct, so loading, decoding, `validate` per-day counts and `trading_days` all agree with the tills. On a UTC sandbox the output is correct, so the bug only shows when you run the entry point with `TZ` set (for example `TZ=Asia/Kolkata`) or inspect the actual epoch bounds passed to the index. Decoys that use the same naive-local idioms but are correct or irrelevant: `time.localtime` in `utils/logging_setup.OperatorFormatter` (operator logs are meant to be server-local); `time.localtime` for snapshot file names, plus `datetime.now()` with `time.mktime` in `storage/archive.SnapshotArchive.cutoff` (a correct use of mktime on a naive local datetime, compared with file mtimes); `datetime.now()` in the report header in `services/reports._header`; `date.today()` for the default `--date` in `cli._default_day`; `datetime.fromtimestamp(..., tz=UTC)` in `timeconv.from_epoch`; `utc_epoch()` (`calendar.timegm`) next to the bug; the UTC-date FX lookup `moment.date()` in `adapters/fx.FxTable.convert` (rates are published per UTC date by design); the `BoundedCache` day cache in the ledger; and `datetime.now(UTC)` in `services/closing`.
